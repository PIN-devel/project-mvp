# MVP-365 · 목표와 변화 / Decision & Progress

## 대표 시안

[통합 프로토타입](../prototype.html)에서 `MVP-365 · 목표와 변화`를 선택한다. `설정한 목표 없음 → 목표 제안 → 목표 선택 → 저장 중 → 저장 확인` 흐름을 확인하고, `저장 실패`, `기존 목표 조회`를 따로 확인한다. **모든 금액과 저장 상태는 Design Sample**이며 실제 계정 조회·저장 성공이 아니다.

이 화면의 중심은 AI가 미래를 예측한다는 감각이 아니라 **내가 한 항목을 정하고 그 선택의 기준을 이해한다는 감각**이다. 밝은 비교·선택 표면이 주 작업 영역이고, Navy 면은 선택한 방향을 기억시키는 역할을 한다. MVP-364의 AI 요약 Hero를 복제하지 않는다.

## 실제 기능 계약

| 기능 | 현재 코드·API | 디자인 적용 |
| --- | --- | --- |
| 목표 목록 조회 | `GET /api/monthly-goals?status=` 선택 사항; 응답에 월, 제목, 카테고리, 비율, 기준·목표 금액, `monthlySave`, 상태, `actualSaved` | 빈 목표/기존 목표/진행 상태를 조회값으로 구분. 현재 FE에서는 **AI 요청 성공 뒤에만 조회**하므로 Stage B에서 독립 조회 연결 필요 |
| 추천 후보 | FE `buildRecommendedGoals(filteredTransactions, getLatestTransactionMonth(...))` | AI 응답이 아니라 거래 카테고리 **금액 합계**에 비율 30/40/50%를 적용한 FE 계산. “AI 추천”으로 부르지 않음 |
| 목표 저장 | `PUT /api/monthly-goals/{goalMonth}` | `title`, `targetCategory`, `reductionRatio`, `baselineAmount`, `monthlySave` 저장. 같은 월은 upsert이므로 기존 목표 교체 가능성을 명시적으로 다룸 |
| 목표 상태 | `active`, `completed`, `stopped`; `PATCH /api/monthly-goals/{goalId}/status` | 진행 중/완수로 표시/중단 상태는 표현 가능. 진행률 수치나 달성 실적은 별도 근거 필요 |
| 목표 월 | 현재 FE는 필터된 거래 또는 전체 거래의 **최신 거래월** 사용, 없으면 현재 UTC 월 | “이번 달” 카피는 최신 거래월과 현재 달이 같다는 확인 없이 사용하지 않음. 시안은 `2026-09` 샘플 명시 |

### 추천의 제한

현재 `buildRecommendedGoals`는 분류 카테고리가 없어도 **`생활비 120,000원` 가상 기준**을 만들어 세 후보를 반환한다. Stage B는 이 fallback을 실데이터 추천처럼 보여주지 않아야 한다. 충분한 실제 분류 근거가 없으면 추천 영역을 Empty로 두고 이용내역 정리로 안내한다. 카테고리 금액 합계는 선택한 필터 기간의 합계이며 월평균이 아니다. 기간이 전체/3개월이면 그 합계를 그대로 “월 기준 금액”이라고 표시하지 않는다. 목표의 월 단위 계약과 필터 기간의 불일치를 명시하거나 월별 같은 기준으로 계산할 수 있는 거래만 사용해야 한다. 이 결정은 기존 거래 데이터로 해결하며 새 Backend 기능을 요구하지 않는다.

## 금액 진실성: 표시 허용선

| 분류 | 근거 | 표시 결정 |
| --- | --- | --- |
| 이용내역 기반 금액 | 실제 조회 거래의 카테고리 합계 | **조회 기간과 범위**를 붙여 “선택 기간의 카테고리 이용 금액”으로 표시 가능. 순지출/월평균/절감과 혼동 금지 |
| 목표 금액 | 저장 응답의 `targetAmount` 또는 FE의 `baselineAmount × (1 − reductionRatio)` | “목표 금액”. 도달하려고 선택한 기준이지 실적이 아님 |
| 계획상 차이 | `baselineAmount − targetAmount`, 현재 추천의 `monthlySave` | “기준 대비 계획상 차이”. 특정 기간에 실제로 아낀 금액이 아님 |
| 전망/예상 절감 | 현재 `buildTrajectoryRows`의 반복 누적 또는 단순 비율 | 검증된 미래 모델이 없으므로 **별도 금액 차트로 표시하지 않음**. 필요한 경우 계산 가정과 기간을 명시해야 함 |
| 실제 절감액/달성률 | 월별 같은 조건의 실제 이용내역 비교와 검증 절차 필요 | **현재 근거 부족으로 표시하지 않음**. `actualSaved` 필드만으로 검증된 실적이라 단정하지 않음 |
| 목표 상태 | 저장된 `status` | “진행 중/완수로 표시/중단” 가능. 상태가 수치 실적을 증명하지 않음 |

`calculateTotalSaved()`는 `active` 목표에 `max(monthlySave * 0.5, baselineAmount - currentAmount)`를 합산하고, `completed`에 `actualSaved ?? monthlySave`를 합산한다. 첫 식의 절반값은 실제 지출 검증과 무관하며, 두 번째 fallback도 목표액을 실적으로 바꾼다. 이 값을 **“누적 절감액”**으로 표시하지 않는다.

`buildTrajectoryRows()`는 시작 월부터 현재+3개월까지, `goal.month <= month`인 모든 진행 목표의 `monthlySave`를 매월 반복 합산한다. `target`에는 매월 최소 12,000원도 더한다. 현재 그래프의 `saved`와 `target`은 과거 실적·미래 전망·목표가 섞여 읽힐 위험이 있다. 이번 디자인은 그 차트를 제거하고 **기준/목표 금액 비교 + 저장 상태 단계**로 바꾼다. 이는 새로운 예측 알고리즘 제안이 아니다.

`PATCH` 완료 동작에서 현재 FE는 `actualSaved ?? monthlySave`를 전달한다. 사용자가 실적을 직접 확인하지 않아도 목표 금액이 `actualSaved`가 될 수 있다. 서버 필드의 존재만으로 “실제 절감” 레이블을 붙이지 않는다. 검증 정책/입력 경로가 마련되기 전에는 성공 상태에 “저장·진행 중”만 표시한다.

## 상태·인터랙션

| 상태 | 화면의 차이 | 행동/피드백 |
| --- | --- | --- |
| 목표 미설정 | Navy 면이 시작 의미를 설명, White 면은 Empty | 분석 결과/실제 분류 내역이 있을 때만 후보를 안내 |
| 추천 있음 | 실제 거래 기반 후보마다 출처 범위·기준/목표/비율 | 후보가 곧 저장된 목표가 아님. 한 개 선택 |
| 선택 중 | 선택 테두리/라디오, 기준↔목표 막대 갱신 | `이 목표 저장하기`가 단일 Primary CTA |
| 저장 중 | 선택 유지, 중복 제출 방지 | 서버 응답 전 “저장 완료” 표시 금지 |
| 저장 성공 | 서버 응답의 제목·월·상태를 ‘내가 선택한 목표’ 면으로 전환 | 한 번의 성공 피드백. 후보와 선택 완료 상태 구분 |
| 저장 실패 | 선택·비율·금액 유지, 해당 작업 근처 오류 | 같은 목표로 재시도 가능. 저장된 목표로 전환 금지 |
| 기존 목표 조회 | 저장 응답을 기준으로 목표·상태 표시 | AI 요청 실패와 독립적으로 조회 가능해야 함 |
| 진행/완수/중단 | 상태와 월 표시 | 실적 근거 없으면 진행률·절감액 미표시. 중단은 과거 선택 기록으로만 표현 |

현 제품은 같은 월을 `PUT`으로 교체하고 목표 상태 변경 버튼을 제공한다. 다른 후보를 선택할 때 기존 월 목표가 있다면 **교체 의도**를 명확히 확인해야 하며, 저장 성공 뒤 서버가 반환한 목표로 갱신한다. 새 목표 생성 기능이나 새 라우트는 설계하지 않는다.

프로토타입의 저장 지연과 성공은 시연용 로컬 전환이다. `저장 실패`는 상태 선택기로 검토한다. 실제 Stage B는 API 오류에 따라 실패를 표시하고 선택을 유지한다. AI 결과→실제 목표 선택·저장·재조회는 MVP-374 해결 후 통합 확인한다.

## UX Writing 예시

- “다음 달에 바꾸고 싶은 한 가지” / “이용내역에서 고를 수 있는 목표”
- “선택 기간의 식비 이용 금액 180,000원” / “목표 금액 126,000원” / “계획상 차이 54,000원”
- “목표로 저장됨 · 진행 중” / “아직 확인된 절감 실적은 없어요”
- “목표를 저장하지 못했어요. 선택한 항목은 그대로 두었습니다. 다시 시도해 주세요.”
- `완수` 조작은 “완수로 표시”가 정확하다. 실제 절감이 인증된 것처럼 축하하거나 누적액에 넣지 않는다.

## Stage B-2 인계

1. `/insights` 안에서 기존 목표 조회를 AI 성공 여부와 분리한다. 인증/라우팅은 유지한다.
2. 추천 후보에 **사용한 거래 기간**을 명시한다. 가상 `생활비 120000` fallback과 다개월 합계의 월 기준 오표시를 해소한다. 근거 없는 후보는 숨긴다.
3. 같은 월 upsert의 교체 의미를 선택/저장 피드백에 반영하고, 서버 성공 응답 뒤에만 ‘선택된 목표’로 갱신한다.
4. `calculateTotalSaved`, `buildTrajectoryRows` 기반의 절감/자산 라벨과 차트는 Stage A의 수치 원칙을 충족할 때까지 표시하지 않는다. 단순히 이름만 바꾸지 않는다.
5. 완료 상태의 `actualSaved` 유입 경로를 검토하고, 검증되지 않은 값은 실제 절감액으로 표기하지 않는다.
6. MVP-374 복구 뒤 실제 AI 성공→목표 선택→저장→재조회 통합 흐름을 별도 검증한다. 디자인 샘플을 테스트 결과로 인용하지 않는다.

## Design Integrity

**Essential**

1. 추천 후보와 실제 저장된 목표를 시각·문구·상태로 구분한다.
2. 목표 선택과 저장 중/성공/실패가 각각 확인 가능하다. 실패 때 선택이 사라지지 않는다.
3. 기준 금액, 목표 금액, 계획상 차이, 확인된 실적을 혼동하지 않는다. 근거 없는 실적/미래 누적 곡선을 그리지 않는다.
4. 기존 목표와 상태는 AI 재생성 실패와 별개로 조회 가능해야 한다.
5. 후보의 계산 근거 기간과 목표 월이 분명하고, 샘플 fallback을 실제 추천처럼 제시하지 않는다.

**Enhancement**

- 기준/목표 금액의 막대 모양과 전환 애니메이션은 숫자·레이블이 남으면 단순화할 수 있다.
- Navy 선택 면의 원형 장식, 카드 hover, 상태 도식의 원형 마커는 줄일 수 있다.
- 추천 후보 카드의 개수·배치는 실제 데이터에 따라 달라도 된다. 단일 선택과 상세 비교는 유지한다.
